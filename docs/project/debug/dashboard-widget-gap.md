## Resolution

root_cause: Two compounding bugs in the v0.4 dashboard. (1) web/src/hooks/useDashboardLayout.js `sanitizeLayouts()` treated a panel's minH/maxH resize constraints as persisted user data (read from the stored blob when present) instead of always re-deriving them from the current PANELS registry, and only clamped stored `h` down to `maxH`. Because houseSummary's `maxH` stayed at 3 across commit 98c4402 (which reduced the *default* h/minH from 2 to 1), any user with a dashboard layout saved before that commit kept rendering the old, oversized h:2 (144px) box forever — the fix never reached already-onboarded users, which is exactly why "prior fix did not fully resolve it." (2) web/src/components/HouseSummaryPanel.jsx's heading and paragraph had no line-count bound, so real (non-empty) content commonly wraps to 2 lines and overflowed a correctly-sized h:1 (64px) box, which DashboardPanel.jsx renders with `overflow-auto` — producing the internal scrollbar the user saw after manually shrinking the panel. This root-cause diagnosis was correct and is unchanged by the corrective pass below.

fix (as of this corrective pass, superseding the b111d05/dd8db08 commits — see the "CORRECTIVE PASS" evidence entries above for why the first attempt needed correcting):
(1) HouseSummaryPanel.jsx — heading keeps `truncate` (single line; real-browser measurement showed it only loses text at genuinely narrow mobile widths with a long room name, an accepted compact-glance tradeoff). Paragraph changed from `truncate` to `line-clamp-2` (Tailwind v4 native, no plugin): the common one-line case (all desktop/tablet widths, any realistic content) renders in full unchanged; only content that needs a 3rd line — narrow phone + worst-case content — loses its tail, with a visible ellipsis instead of `truncate`'s silent single-line cut of a sentence that commonly has two clauses.
(2) dashboardPanels.js — houseSummary's desktop (`lg`) values are unchanged from the first pass: `h:1, minH:1, maxH:1` (measured in a real browser to fit real content with ~8px slack at any width >=768px). Restored `smH:2` for mobile (the paragraph commonly wraps to 2 lines in a single narrow column even for ordinary content — h2(20px)+2-line-p(48px)=68px alone exceeds a 64px row before any padding, so no amount of spacing-trimming makes h:1 work on mobile). Added two NEW per-breakpoint registry fields, `smMinH:2` and `smMaxH:2`, because `maxH:1`/`minH:1` shared across both breakpoints would otherwise either (a) clamp a correctly-persisted mobile h:2 back down to 1 on the user's very next page load (react-grid-layout persists a layout from its own mount effect — see useDashboardLayout.js lines 143-151 — so "next load" is the second page view, not an edge case), or (b) leave anyone who loaded the dashboard on mobile while `maxH:1` WAS shared (i.e. during the b111d05/dd8db08 window) stuck at a clamped-and-persisted `sm` h:1 forever, since minH:1 alone can't force a stored value back up and mobile resize is disabled.
(3) useDashboardLayout.js `sanitizeLayouts()` — `minH`/`maxH` are now both read per-breakpoint: `(bp === 'sm' ? panel?.smMinH : null) ?? panel?.minH ?? 1` and `(bp === 'sm' ? panel?.smMaxH : null) ?? panel?.maxH`. No other panel in the registry declares `smMinH`/`smMaxH`, so this is a no-op for every panel except houseSummary.
